базові сторінки
1. сторінка команд - відображає всі наявні команди в баг-трекері (добавити аватари для команд для кращого орієнтування (атавар команди дозволить швидше візуально знахоидит потрібну тобі команду, так як це можливо в jira)
2. сторінка канбан - відображення тікетів команди, сторінка повинна мати змогу відображати тікети розбивши по окремим працівникам для зручності пошуку, та швидкими фільтрами по працівнику etc
3. сторінка backlog\agile - відображення спринтів, беклогу - для керування спринтами команди
3. дашборд панель користувача - створена для швидкого переміщення до канбану своєї команди, відображення тікетів користувача, пошук за допомогою збережених фільтрів пошуку та іншої швидкої статистики
4. профіль користувача, відображає групи доступу користувача, його ім'я, роль, команду, аватарку, вхід з яких пристроїв здійснено, активність, etc - для інших користувачів дозволяє швидко зрозуміти з якої команди цей користувач - для адмінів теж швидко зрозуміти що це за користувач, побачити останню активність користувача (логування часу, відповіді в тікети, внесення змін до тікетів) etc. - також профіль користувача дозволяє зробити edit - змінити аватар, відредагувати ім'я, змінити налаштування 2fa, підключити github або google до аккаунту etc....
5. сторінка preferences - сторінка яка дозволяє керувати відображенням баг-трекера, як буде виглядати бокова панель, тема біла чи чорна etc...





6. адмінка - набір сторінок які призначені для адміністрування баг-трекеру, керування банерами (для сповіщенням про наприклад недоступність багтрекера для оновлення системи чи реіндексації etc.), юзер менеджементу та контролю доступів, керування командами, статиски про здоров'я систем баг-трекеру, доступ до логів системи - активність користувачів, кількість входів, кількість користувачів з 2fa, входи користувачів інша корисна системна аналітика etc...
7. сторінка пошуку - створенна для пошуку тікетів, пошуку за збереженими фільтрами, швидкого визначення нових тікетів (приклад базового воркфлоу зі сторінкою користувач використовує збережений пошуковий запит для показу всіх тікетів команди починаючи з найновіших - після чого користувач бачить тікети які ще не були взяті та бере собі або призначає для колеги. Приклад 2 - користувач робить вибірку всіх своїх тікетів в команді core - починаючи з найновіших)

8. сторінка логування часу - окрема або під сторінка команди для логування часу команд

9. аналітика - набір сторінок - для відображення бізнес аналітики для менеджерів, доступ до сторінок мають адміни та менеджери або любі користувачі з відповідним доступом виданим в RBAC юзер менеджемент

Сервіси ядра

Сервіс автентифікації з усіма його зіставними модулями (2fa, turntile etc...) повинні пройти перевірку на вразливість безпеки та якість реалізації

Завершений сервіс - наприклад сервіс автентифікації повинен бути задокументований - документація повинна описати архітектуру сервісу, практичну частину реалізації, використані залежності, структуру модулів, опис основних елементів та їх роботи документація повинна місти діаграми mermaid там де це є корисним

Документація зберігається в папці info у відповідному пвдкаталозі сервісу
Наприклад
info/core/auth/*.md
info/frontend/...
Також в каталогах допускається збереження діаграм в PNG форматі та форматі mermaid якщо вони зашиті в сам md файл


Розробка супроводжується обов'язковим плануванням, наприклад при розробці сторінки адмінки потрібно мати розробки з підготовки md плану (такі документи зберігаються в info/planning/... )

10. Головна сторінка - сторінка яка зустрічається незалогіненого користувача - головниц акцент сторінки на логіні та реєстрації користувача, та короткому описі можливостей системи та плюсів

12. Логін сторінка - форма логіну з підтримкою входу через GitHub або google Oauth
